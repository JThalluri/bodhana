# Phonics Constructs Pipeline — Build Specification (Phase 1 of 5)

**Target consumer:** IDE build agent (Cursor / Aider / Copilot Workspace / human dev).
**Phase scope:** constructs authoring format, compiler, build-time validation, and a regression
test harness. **No Bodhana UI changes. No `PhonicsConstructor` engine refactor.** Those are
Phase 3 (engine) and Phase 4 (Dictionary Builder) — see §11.
**Spec version:** 1.0.0
**Required inputs** (ship alongside this spec, read before writing any code):
- `phonics-regression-fixtures-v2.md` — rationale and human-readable findings log.
- `phonics-regression-fixtures.v2.yaml` — **authoritative, machine-readable test corpus.** Load
  this directly; do not re-derive fixtures from the `.md` file or from the old prototype.
- `phonics-phase2-backlog.md` — deliberately deferred items. **Do not silently resolve any item
  in this file as a side effect of Phase 1 work.** If Phase 1 work touches a backlog item, update
  the backlog file, don't just fix it in passing.

---

## 1. Purpose

Replace the current state — construct tables embedded as JS object literals and comments inside
`PhonicsConstructor.js`, with no independent versioning, no validation, and at least one
confirmed silent-overwrite bug in production history (the `rookie`/`hoodie` dual-override case) —
with:

1. A single human/LLM-editable **authoring file** (YAML) that can be enriched iteratively,
   outside the repo if needed, without touching engine code.
2. A **compiler** that turns that authoring file into a validated, engine-ready JSON artifact.
3. **Build-time validation** that hard-fails on the specific bug classes already found in this
   data (duplicate/colliding keys, unreachable patterns, under-tested branches) rather than
   shipping them silently.
4. A **regression harness** that proves the compiled output matches the agreed fixture corpus,
   and keeps proving it on every future enrichment.

This phase deliberately produces **no runtime consumer**. The compiled JSON this phase produces
is the contract that Phase 2 (Constructs Workbench) and Phase 3 (engine refactor) will both
build against — get the shape right here, because changing it later means redoing both.

### 3.2 Why `vowelTeamExceptions` is a flat row array, not a nested object

The current JS source keys this table by word (`{ bread: {ea:'short_e'}, ... }`). **This is the
exact structural cause of the `rookie`/`hoodie` bug** — if a word needs to appear with two
different override pairs, or if the same word gets accidentally declared twice across two
sections of a large file, the second declaration silently overwrites the first, because object
keys can only hold one value per key.

The YAML schema instead uses a flat array of `{word, pattern, sound, note?}` rows. Multiple rows
for the same word (e.g. `cookie` needing both `ie:long_e` and `oo:oo_short`) are simply multiple
array entries — there is no overwrite mechanism to trigger. The corresponding hard rule (§5.4) is:
**no two rows may share the same `(word, pattern)` pair.** That's the actual constraint that
matters (two different *sounds* claimed for the same word+pattern is the real contradiction);
two different *patterns* for the same word is completely normal and must stay legal.

The `note` field is **not** author-only decoration — it compiles through into the JSON output
(§4.2) so that Phase 2's Workbench can show it as part of the context bundle. Write real
rationale here, not filler.

## 4. Compiler — `scripts/build-constructs.mjs`

### 4.1 Behavior

1. Read `constructs/phonics-constructs.yaml`.
2. Run full validation (§5). **On any validation failure, print every failure found (not just
   the first), then exit non-zero.** Never produce partial or best-effort output.
3. Compile to the JSON shape in §4.2.
4. Compute a content hash of the source YAML (e.g. sha256) and stamp it into the output as
   `sourceHash`, alongside `generatedAt` (ISO timestamp) and `schemaVersion` (copied from source).
5. Write to `src/phonics/generated/phonics-constructs.json`.

### 4.2 Compiled JSON shape

```json
{
  "schemaVersion": "1.0.0",
  "generatedAt": "2026-10-01T12:00:00.000Z",
  "sourceHash": "sha256:...",

  "patternCategories": { "digraphs": [...], "floss": [...], "...": "..." },
  "patternCategoryDefaultLevels": { "digraphs": 2, "...": "..." },
  "patternLevelOverrides": { "gh": 4, "...": "..." },
  "scopeLevels": [ { "level": 1, "name": "...", "desc": "..." } ],
  "soundLabels": { "long_a": "/ā/ (cake)", "...": "..." },
  "defaultVowelSound": { "ai": "long_a", "...": "..." },

  "vowelTeamExceptions": [
    { "word": "bread", "pattern": "ea", "sound": "short_e", "note": null }
  ],

  "compoundParts": ["some", "any", "..."],
  "rootWords": ["run", "hop", "slim", "..."],
  "suffixStripRules": [
    { "suffix": "tion", "minStem": 3, "always": true, "undouble": false, "edOnly": false }
  ]
}
```

Note that `vowelTeamExceptions` stays an **array** in the compiled output too — grouping rows
into a word-keyed lookup map is explicitly an *engine* concern (Phase 3), not something this
compiler should decide. Keeping the array shape here means Phase 3 can choose its own in-memory
lookup structure without this phase needing to be revisited.

### 4.3 `schemaVersion` — what it is and isn't

This is **not** a release/semver number — once bundled into the SPA via Vite, ordinary git
history is the versioning. `schemaVersion` exists purely as an internal safety rail: if someone
hand-edits the YAML's *shape* (renames a field, restructures a section) in a way that still
parses as valid YAML but no longer matches what a consumer expects, a schema mismatch should be
a loud build failure, not a quiet wrong-output bug. Bump it only when the *shape* of the compiled
output changes, never for ordinary content edits (new exception rows, new compound parts, etc).

### 4.4 Why the compiled JSON is generated, not committed

This project started this whole effort because of exactly this failure mode: `PhonicsConstructor.js`
claimed `VERSION = '2.3.0'` while its actual table contents matched the `2.3.1` spec, and a
separately-exported `phonics-dictionary.csv` didn't match either. Three "truths," silently
diverged. Committing a generated artifact recreates that risk — a stale committed JSON could
silently diverge from its own YAML source. Instead: `.gitignore` the generated file, and wire
`prebuild`, `predev`, and `pretest` npm scripts (§7) so it is *always* freshly regenerated and
validated before anything consumes it. There is structurally no way for it to go stale.

## 5. Validation rules (permanent, build-blocking)

These four replace the one-off manual audits performed during fixture rationalization. Implement
each as an independent, named check in `scripts/constructs-validate.mjs` so failures report
clearly (which rule, which specific pattern/word, why).

### 5.1 Reachability

Every pattern string declared anywhere in `patternCategories` must appear as an exact token in
at least one `tokenizer` fixture's `graphemes` field (split on `|`).

```js
// Pseudocode
function checkReachability(constructs, fixtures) {
  const declared = new Set(allPatternsFlattened(constructs.patternCategories));
  const produced = new Set();
  fixtures.tokenizer.forEach(f => f.graphemes.split('|').forEach(tok => produced.add(tok)));
  const unreachable = [...declared].filter(p => !produced.has(p));
  if (unreachable.length) fail('reachability', unreachable);
}
```

### 5.2 No cross-category pattern collisions

No pattern string may be declared in more than one category in `patternCategories`. This
replaces reconciling the documented tie-break order (`clusters3 > trigraphs > digraphs > ...`)
against the code's actual category-declaration-order tie-break — by banning collisions outright,
which order wins becomes structurally irrelevant.

```js
function checkNoCrossCategoryCollisions(constructs) {
  const seen = new Map(); // pattern -> category
  for (const [cat, patterns] of Object.entries(constructs.patternCategories)) {
    for (const p of patterns) {
      if (seen.has(p)) fail('cross-category-collision', { pattern: p, categories: [seen.get(p), cat] });
      seen.set(p, cat);
    }
  }
}
```

### 5.3 Suffix/exception branch coverage

Every `suffixStripRules` entry (by its `suffix` value) and every tier of exception lookup
(`direct`, `suffix-stripped`, `compound-scan`) must be exercised by at least one
`vowelTeamSounds` or `syllableSplit` fixture. For suffix rules specifically: at least one
`syllableSplit` fixture must have gone through `tryStripSuffix` matching that exact suffix.

```js
function checkSuffixAndExceptionBranchCoverage(constructs, fixtures) {
  const suffixesUsed = new Set();
  fixtures.syllableSplit.forEach(f => {
    const matchedSuffix = constructs.suffixStripRules.find(r => f.word.endsWith(r.suffix));
    if (matchedSuffix) suffixesUsed.add(matchedSuffix.suffix);
  });
  const missing = constructs.suffixStripRules
    .map(r => r.suffix)
    .filter(s => !suffixesUsed.has(s));
  if (missing.length) fail('suffix-rule-coverage', missing);
  // Direct/suffix-stripped/compound-scan tier coverage: verify by replaying lookupException's
  // three tiers against fixtures.vowelTeamSounds and confirming each tier is hit at least once.
  // (Exact replay logic depends on Phase 3's engine; for Phase 1, a simplified standalone
  // re-implementation of the three-tier lookup is acceptable here, since this is validation-only
  // code, not the shipped engine.)
}
```

### 5.4 Exception-table self-verification (the big one — replaces manual audit entirely)

Every row in `vowelTeamExceptions` is auto-verified against its own stated output — zero
authoring cost, and it doubles as a typo guard.

```js
function checkExceptionTableSelfConsistency(constructs) {
  const seenPairs = new Set(); // "word|pattern"
  constructs.vowelTeamExceptions.forEach(row => {
    const key = `${row.word}|${row.pattern}`;
    if (seenPairs.has(key)) fail('duplicate-exception-row', key); // same word+pattern twice
    seenPairs.add(key);

    if (!row.word.includes(row.pattern)) {
      fail('exception-pattern-not-in-word', { word: row.word, pattern: row.pattern }); // typo guard
    }
    if (!constructs.soundLabels[row.sound]) {
      fail('exception-unknown-sound', { word: row.word, sound: row.sound });
    }
    if (!constructs.patternCategories.vowelTeams.includes(row.pattern)) {
      fail('exception-pattern-not-a-vowel-team', { word: row.word, pattern: row.pattern });
    }
  });
}
```

### 5.5 Additional structural checks (fold into the same module)

- `patternLevelOverrides` keys must each exist in some `patternCategories` list (hard-fail if not).
- `defaultVowelSound` keys must be a subset of `patternCategories.vowelTeams` (hard-fail if not).
- Every sound value referenced anywhere (`defaultVowelSound`, `vowelTeamExceptions[].sound`) must
  have a corresponding `soundLabels` entry (hard-fail if not).
- `compoundParts` entries must be length ≥ 2; `rootWords` entries must be length ≥ 3 — **hard-fail
  on violation, do not silently drop short entries** (current runtime behavior silently drops
  them; this compiler must not repeat that pattern).
- `suffixStripRules` entries must have a non-empty lowercase-alpha `suffix` and a positive integer
  `minStem`.

## 6. Regression harness — `tests/constructs/*.test.js`

- Load `constructs/fixtures/phonics-regression-fixtures.v2.yaml` and the compiled
  `src/phonics/generated/phonics-constructs.json`.
- For each fixture category (`tokenizer`, `syllableSplit`, `vowelTeamSounds`), run the
  corresponding check using the **real, permanent** `tokenize()`, `splitSyllables()`, and
  `vowelTeamSounds()` functions from `src/phonics/core/` (built as part of this phase's
  deliverables, §2), driven off the compiled JSON. This is not a throwaway reimplementation —
  this phase builds the actual shared logic that Phase 2's Workbench and Phase 3's engine both
  import unmodified. This phase does not touch or depend on the legacy `PhonicsConstructor.js`
  file at all; it's building the real replacement from day one.
- **`expectedFailure: true` fixtures** (currently: `gingerbread`, `reindeer`, `readable`,
  `visible` — see the fixture YAML): assert and report, but do not fail the build. Additionally:
  - If an `expectedFailure` fixture **passes**, emit a warning naming it and pointing at
    `phonics-phase2-backlog.md` — this is a signal the backlog item may be closeable.
  - If a **non**-`expectedFailure` fixture fails, that's a hard build failure — this is a real
    regression, full stop.
- All four validation rules from §5 run as part of the same `npm test` pass, not just at compile
  time — a hand-edited-but-not-recompiled JSON should never silently pass tests.

## 7. `package.json` wiring

```json
{
  "scripts": {
    "build:constructs": "node scripts/build-constructs.mjs",
    "prebuild": "npm run build:constructs",
    "predev": "npm run build:constructs",
    "pretest": "npm run build:constructs",
    "test": "vitest run",
    "test:constructs": "vitest run tests/constructs"
  }
}
```

`build:constructs` must be idempotent and side-effect-free beyond writing the one output file —
safe to run repeatedly, safe to run concurrently with itself being a no-op race (last-write-wins
is acceptable since output is fully deterministic from the same input).

## 10. Acceptance criteria

1. `node scripts/build-constructs.mjs` run standalone succeeds and produces
   `src/phonics/generated/phonics-constructs.json`.
2. Running it again with no YAML changes produces byte-identical output (determinism).
3. Deliberately introducing a duplicate `(word, pattern)` row in `vowelTeamExceptions` causes a
   build-blocking failure naming the exact word and pattern.
4. Deliberately re-adding `rk` to `blends` and running tests surfaces it as a reachability
   failure (§5.1) — proving the "would have caught this" claim from the fixture rationalization
   work is actually enforced, not just documented.
5. `npm test` passes with all `expectedFailure: false` fixtures green and the four
   `expectedFailure: true` fixtures reported as known-failures, not build-blocking.
6. Flipping any `expectedFailure: true` fixture to passing (e.g. after manually patching
   `COMPOUND_PARTS` to include `ginger`) causes the harness to emit the "may be closeable, check
   the backlog" warning described in §6.
7. Zero references to `PhonicsConstructor.js` exist anywhere in this phase's new code — Phase 1
   is fully independent of the legacy engine file.
8. `constructs/README.md` documents the YAML schema well enough that someone unfamiliar with this
   spec could add a new exception row correctly without re-reading this document.
9. `scripts/constructs-compile-core.mjs` exports `compileConstructs()` as a pure function with
   zero file I/O inside it — verified by calling it directly with an in-memory object (no disk
   access) and confirming it returns the compiled shape with no error.
10. `src/phonics/core/*.mjs` contains zero references to "temporary," "throwaway," or similar in
    comments, and zero references to the legacy `PhonicsConstructor.js` file anywhere in this
    phase's code (restates criterion 7 at the core-module level specifically, since this is the
    file set most likely to be miscategorized as scaffolding if this isn't explicit).

  action, tabbed info-pane, Detail view, flag-for-review export.
- **Phase 5 — Phonics Worksheets module**: thin worksheet UI consuming Phase 4's shared components.

this sequencing is that each phase proves its foundation before the next one builds on it.
